== Overview

The Torg Codex application stores game data for the TORG RPG in *257 YAML files* located under `src/main/resources/db/`.
These files contain spells, miracles, perks, items, threats, vehicles, races, cosm descriptions, and other game entities.

Each entity typically has a `text` field (and sometimes a `worldLaws` field) containing rich content authored in a mix of *Markdown* and a *custom markup language* specific to the Torg Codex.

== YAML File Organisation

The YAML files are organised by product and entity type:

[source]
----
src/main/resources/db/
+-- cosms.cosms.yml                    <1>
+-- groups.groups.yml
+-- darkness_devices.threats.yml
+-- articles/
|   +-- possibility_tokens.articles.yml
|   +-- changelog.articles.yml
|   +-- credits.articles.yml
+-- books/
|   +-- material/                      <2>
|   +-- campaign/
|   +-- delphi-missions/
+-- decks/                             <3>
+-- infiniverse/                       <4>
----
<1> Core data files shared across all products
<2> Sourcebook and supplement content (222 files)
<3> Card deck images and definitions
<4> Community and creator content

== Multi-valued Catalog References

Catalog entries may belong to zero, one, or several cosms. The domain and persistence
models represent these assignments as sets of stable cosm slugs rather than encoded list
strings. Miracle, power, and spell lists use the same set-based representation for their
unlocking-perk slugs.

The `cosm` query parameter remains singular and accepts a slug such as `core-earth`.
An entry is returned when that slug is one member of its assigned set. In responses, a
single known cosm retains its UUID and display name. Several cosms are exposed through the
existing `cosm` object with `id = null` and alphabetically sorted display names joined by
comma-space. Unknown slugs remain visible as raw values.

The existing `unlockingPerk` response field also retains its type. One assignment remains
one slug; several assignments are sorted and joined by comma-space. Unlike cosms, perk
slugs are intentionally not resolved to display names.

== Imported Prose Normalization

Legacy imports may contain complete Python-style list literals in `additionalFeatures`,
threat `quote`, or spell-list `notes`. The post-import Liquibase repair converts one
statement to plain text and several statements to a source-ordered Markdown list.
Malformed values, partial lists, and ordinary prose containing brackets remain unchanged.
The resulting Markdown continues through the normal rendering and censoring pipeline.

== Custom Markup Language

The `text` fields use standard Markdown enriched with four custom markup constructs:

Conditional blocks:: `<IF:product-id>...</IF>` -- content shown or hidden based on which products the user owns.
Entity cross-references:: `<type:id>` -- links to other game entities (e.g., `<perk:negation>`, `<cosm:aysle>`).
Raw HTML injection:: `[HTML:content]` -- trusted HTML passed through verbatim.
Game tokens:: `[shock]`, `[BD]`, `[possibilities]` -- icons representing game mechanics.

See xref:08_concepts/torg_data/markup-syntax.adoc[] for the full syntax reference and xref:08_concepts/torg_data/markup-parser.adoc[] for the parser implementation.

== Rendering Pipeline

The markup is processed through a five-stage pipeline, each stage transforming the text string:

[source]
----
raw text + ownedProducts
    |
    v
1. ConditionalBlockProcessor   -- resolve <IF:...>...</IF>
    |
    v
2. EntityReferenceProcessor    -- <type:id> -> HTML links
    |
    v
3. RawHtmlProcessor            -- [HTML:...] -> raw HTML
    |
    v
4. GameTokenProcessor          -- [token] -> <span> icons
    |
    v
5. MarkdownProcessor           -- Markdown -> HTML (commonmark-java)
    |
    v
rendered HTML
----

The pipeline is coordinated by `TorgMarkupService`, a Spring `@Service` in the `de.paladinsinn.torg.codex.data.markup` package of the `torg-codex-data` library module.

== Security Layer

The `torg-codex-data` module has no Spring Security dependency.
It accepts a plain `Set<String>` of product IDs and does not know how those IDs were obtained.

The `torg-codex` web module provides `ProductOwnershipResolver` and
`CurrentUserCensorFactory`, which read the current user's Spring Security authorities,
map every `ROLE_<product-id>` authority to the product-id `<product-id>`, and delegate
to `TorgMarkupService`. DriveThruRPG authentication and its security principals live in
the `torg-codex-application` module; the data module remains unaware of Spring Security.

See xref:08_concepts/torg_data/role-mapping.adoc[] for details.
