= Role Mapping: Spring Security to Product IDs
include::partial$config.adoc[]

== Overview

The TORG markup language uses `<IF:product-id>` / `<IF:!product-id>` conditional blocks to gate content behind product ownership.
At runtime, the rendering pipeline needs to know which products the current user owns so it can resolve those conditions.

This page describes how Spring Security roles are mapped to product IDs and how the single ownership-resolution mechanism
(`CurrentUserCensorFactory` delegating to `ProductOwnershipResolver`) bridges the security layer and the markup pipeline.


== Role Naming Convention

Each TORG product corresponds to one Spring Security authority using the standard `ROLE_` prefix:

[source]
----
Spring Security authority   product-id (used in markup)
--------------------------  ---------------------------
ROLE_core-rulebook       -> core-rulebook
ROLE_sourcebook-aysle    -> sourcebook-aysle
ROLE_delphi-missions     -> delphi-missions
ROLE_digital-orrorsh     -> digital-orrorsh
----

The mapping rule is simple: strip the `ROLE_` prefix.
Everything that follows becomes the product-id matched against `<IF:product-id>` tags in the markup.

Non-product authorities (e.g., OAuth2 scopes such as `SCOPE_read`) do not carry the `ROLE_` prefix and are therefore ignored by the resolver.

This mechanism is *principal-type independent*: ownership is derived purely from the `ROLE_<codex-id>` `GrantedAuthority`
entries on the current `Authentication`, regardless of whether that context was established by a DriveThruRPG API key, an
OIDC/Keycloak token, or any other authentication method (constitution Principle V).


== Markup Semantics Revisited

With the role mapping in place, the two conditional block forms have the following security semantics:

.Conditional block semantics relative to Spring Security roles
[cols="<.<4,<.<8",options="header",frame="topbot",grid="rows"]
|===
| Markup | Rendered when

| `<IF:core-rulebook>…</IF>`
| The authenticated user holds the authority `ROLE_core-rulebook`

| `<IF:!core-rulebook>…</IF>`
| The authenticated user does *not* hold `ROLE_core-rulebook`, or is not authenticated at all

|===

The second form is intentionally used as a "teaser" or "you need this book" notice: unauthenticated and anonymous users see only the negated blocks.


== Unauthenticated and Anonymous Users

If no `Authentication` is present in the security context, or the authentication is not flagged as authenticated, the resolved product-id set is *empty*.
As a result:

* All `<IF:product-id>` (positive) blocks are suppressed.
* All `<IF:!product-id>` (negated) blocks are shown.

This gives anonymous visitors the minimal, non-gated view of all content without requiring any authentication check in the rendering code itself.

NOTE: In production, the configured anonymous principal (`NotLoggedInUserDetails`) always carries `ROLE_core-rulebook`,
so anonymous visitors additionally see the free-tier core-rulebook content.


== Architecture

The security integration lives entirely in the `torg-codex` application module.
The `torg-codex-data` library module has no Spring Security dependency; it accepts a plain `Set<String>` of product IDs and does not know how that set was obtained.

There is exactly *one* production mechanism that derives product ownership for censoring (constitution Principle V):
`CurrentUserCensorFactory`, which delegates to `ProductOwnershipResolver`. Both live in the
`de.paladinsinn.torg.codex.api.security` package.

[source]
----
torg-codex-data (no Spring Security dependency)
└── TorgMarkupService
        render(String rawText, Set<String> ownedProducts)
            |
            └─> ConditionalBlockProcessor.process(text, ownedProducts)
                    Resolves <IF:...> blocks against the Set
└── Censor
        of(TorgMarkupService, Set<String> ownedProducts)
        apply(String rawText) -> render(rawText, ownedProducts)

torg-codex (Spring Security on classpath)
└── api.security.ProductOwnershipResolver
        resolve() : Set<String>                          <1>
└── api.security.CurrentUserCensorFactory
        create() : Censor                                <2>
----
<1> Reads `ROLE_*` authorities from `SecurityContextHolder`, strips the prefix, returns the owned product-id set. Performs no I/O.
<2> Calls `ProductOwnershipResolver.resolve()` and constructs a request-scoped `Censor.of(markupService, ownedProducts)`.


== Rendering Order

The markup pipeline order is fixed and unchanged by ownership resolution — only the `Set<String> ownedProducts` input
is computed by the resolver. `TorgMarkupService.render(rawText, ownedProducts)` applies its stages in this order:

. Conditional product blocks (`<IF:...>` / `<IF:!...>`)
. Entity references
. Raw HTML
. Game tokens
. CommonMark (Markdown)


== ProductOwnershipResolver

`ProductOwnershipResolver` is a Spring `@Component` in the `de.paladinsinn.torg.codex.api.security` package of the `torg-codex` module.
It is the sole component that reads product ownership from the security context.

Internally it extracts the owned product IDs from the current authentication:

[source,java]
----
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
// null or unauthenticated -> empty set
// authenticated -> stream ROLE_* authorities, strip prefix
if (auth == null || !auth.isAuthenticated()) {
    return Set.of();
}
return auth.getAuthorities().stream()
    .map(GrantedAuthority::getAuthority)
    .filter(a -> a.startsWith("ROLE_"))
    .map(a -> a.substring("ROLE_".length()))
    .collect(Collectors.toUnmodifiableSet());
----


== Usage in Web Controllers

The 15 gated REST controllers do not resolve ownership themselves. They inject `CurrentUserCensorFactory`, obtain a
request-scoped `Censor`, and pass it to their MapStruct mapper as a `@Context` parameter:

[source,java]
----
@RestController
@RequestMapping("/api/cosms")
@RequiredArgsConstructor
public class CosmController {

    private final CatalogQuery<Cosm> catalogQuery;
    private final CosmMapper mapper;
    private final CurrentUserCensorFactory censorFactory;

    @GetMapping("/{id}")
    public ResponseEntity<CosmDetailDto> getById(@PathVariable UUID id) {
        final Censor censor = censorFactory.create();
        return catalogQuery.findById(id)
                .map(e -> mapper.toDetail(e, censor))
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }
}
----

The controller does not handle roles itself.
`CurrentUserCensorFactory` → `ProductOwnershipResolver` resolves the current user's product ownership transparently.


== Module Boundary

[cols="<.<4,<.<8",options="header",frame="topbot",grid="rows"]
|===
| Module | Responsibility

| `torg-codex-data`
| Markup parsing pipeline (`TorgMarkupService`, `ConditionalBlockProcessor`, `Censor`, …).
No knowledge of Spring Security or HTTP sessions.
Accepts `Set<String> ownedProducts` as a plain parameter.

| `torg-codex`
| Spring Security integration (`ProductOwnershipResolver`, `CurrentUserCensorFactory`).
Extracts product IDs from the authenticated user's `ROLE_*` authorities and passes them to the data module.
|===

This boundary keeps the data module independently testable and reusable without the application container.


== Test Strategy

`ProductOwnershipResolverTest` covers the following scenarios using plain JUnit 5 (no Spring context required):

.Test scenarios for ProductOwnershipResolver
[cols="<.<7,<.<5",options="header",frame="topbot",grid="rows"]
|===
| Scenario | Expected product-id set

| No `Authentication` in security context
| Empty set

| Unauthenticated `Authentication` (`isAuthenticated() == false`)
| Empty set

| Anonymous authentication with `ROLE_ANONYMOUS`
| `{ "ANONYMOUS" }` (stripped prefix)

| Authenticated (generic) principal with `ROLE_core-rulebook`, `ROLE_delphi-missions-aysle`
| `{ "core-rulebook", "delphi-missions-aysle" }`

| Non-`ROLE_` authority present (e.g., `SCOPE_read`)
| Filtered out; not included in the set

| Unknown/stale `ROLE_` id (no matching `<IF:...>` block)
| Included as-is; inert during rendering

|===

In addition, `CensoringDifferentialTest` asserts — via live MockMvc requests to the Aysle cosm detail endpoint — that an
anonymous request and a `ROLE_sourcebook-aysle` owner request produce genuinely *different* `worldLaws` output, and
`CensoringSingleMechanismArchitectureTest` enforces that exactly one component derives ownership from `GrantedAuthority`.
