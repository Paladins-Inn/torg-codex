= Observability Concept with Spring Boot, Prometheus, and JSON Logging
include::partial$config.adoc[]

Observability refers to a system’s ability to provide insights into its internal state by exposing external outputs. It is typically built on three pillars: *Logging*, *Monitoring*, and *Alerting*.

== 🔍 Logging

Logging captures structured or unstructured information about system events. In a production-ready setup, logs are written in JSON format to facilitate automated processing and analysis.

=== Technology: Spring Boot + JSON Logging

Use Spring Boot native structured JSON logging, with Logback supplied by the
standard Boot logging starter. A separate Logstash encoder dependency or custom
encoder configuration must not be used. This replaces the former LogstashEncoder
prescription; see xref:09_architecture_decisions/017_spring-boot-structured-logging.adoc[ADR-017].

Production console configuration in `application.yaml` of the `torg-codex` module:

[source,yaml]
----
logging:
  structured:
    format:
      console: ecs
----

If file logging is enabled, also set `logging.structured.format.file: ecs`.
Application logging continues to use Lombok `@Slf4j` and follows the operational audience and severity rules defined in xref:08_concepts/logging-policy.adoc[Logging Policy for Operations and Support] ({adr-022}). Fields supplied through
`log.atWarn().addKeyValue(...)` must appear in emitted JSON. Verify serialized
output under production logging configuration; capturing a Logback event alone
does not prove that the configured output preserves structured fields.

* Example log output:
[source,json]
----
{
  "@timestamp": "2026-11-14T22:00:00Z",
  "log.level": "INFO",
  "log.logger": "com.example.MyService",
  "message": "User successfully created",
  "event.action": "user-created"
}
----

=== Catalog entries without product assignment (DRM)

The domain-level DRM ({adr-019}) hides catalog entries without any product assignment from every caller. Each
encounter (lists, cosm-filtered lists, single entries, embedded references and cosm reference resolution) is
reported once, without deduplication across requests, by `CatalogAccessObservabilityAdapter`:

[cols="1,3",options="header"]
|===
| Aspect | Value
| Level | `WARN`
| Message | `Catalog entry without product assignment hidden by DRM: area=…, id=…, name=…`
| Structured fields | `catalogArea` (area tag, e.g. `spell-list`), `entryId`, `entryName`
| Forbidden content | caller identity, principal, authorities, owned products, API keys
|===

`StructuredLoggingTest` parses the emitted ECS JSON of this warning under the production configuration and verifies
the structured fields and the absence of caller data.

== 📊 Monitoring

Monitoring collects metrics (e.g. latency, memory usage, throughput) to continuously observe system performance and health.

=== Technology: Spring Boot Actuator + Prometheus

* `spring-boot-actuator` exposes metrics via the `/actuator/metrics` endpoint.
* Integration with `micrometer` enables Prometheus as a metrics backend.

=== Example configuration (application.yml)

[source,yaml]
----
management:
  endpoints:
    web:
      exposure:
        include: prometheus
  metrics:
    export:
      prometheus:
        enabled: true
----

* Prometheus is configured with a `scrape` job to periodically collect metrics:

[source,yaml]
----
scrape_configs:
  - job_name: 'spring-boot-app'
    static_configs:
      - targets: ['localhost:8080']
----

=== Catalog DRM counter

Every encounter of a catalog entry without product assignment increments the counter
`torg.codex.catalog.entries.without.products` (Prometheus:
`torg_codex_catalog_entries_without_products_total`). Its only tag is `area` (one of the 14 catalog area tags),
keeping the cardinality bounded; entry ids, names and caller data are never used as tags. The counter is
monotonic per application instance: use its increase over time, not its absolute value, to detect current data gaps.

=== Catalog Usage & Roll-Up Counters

Channel-agnostic catalog usage across both the Web UI and `/api/*` REST endpoints is reported by the core query
services through `CatalogUsageObserver` and exported by `CatalogUsageObservabilityAdapter` without recording
caller identity, credentials, or `ROLE_<codex-id>` authorities:

* **Granular counters (4 meter families)**:
- `torg.codex.catalog.usage.category\{category}` — per-category reads across all 17 `CatalogArea` slugs.
- `torg.codex.catalog.usage.cosm\{cosm}` — accesses and validated cosm filters per known cosm slug.
- `torg.codex.catalog.usage.grouping\{dimension,group}` — accesses and validated facet filters across known Perk Groups, Spell/Miracle/Power Lists, Tags, Item/Vehicle Types, Clearances, and Races.
- `torg.codex.catalog.usage.detail\{category,entry,outcome}` — single-entry lookups by canonical slug across `drm-granted`, `public-reference`, `teaser`, and `not-found` (using the bounded sentinel `entry="_not_found_"` so unknown URLs never create unbounded time series).
* **Outcome roll-up counters (4 untagged totals)**:
  - `torg.codex.catalog.usage.outcome.drm.granted`
  - `torg.codex.catalog.usage.outcome.public.reference`
  - `torg.codex.catalog.usage.outcome.teaser`
  - `torg.codex.catalog.usage.outcome.not.found`
* **Metric-family roll-up counters (4 untagged totals)**:
  - `torg.codex.catalog.usage.family.category`
  - `torg.codex.catalog.usage.family.cosm`
  - `torg.codex.catalog.usage.family.grouping`
  - `torg.codex.catalog.usage.family.detail`

== 🚨 Alerting

Alerting generates notifications based on defined thresholds in metrics, enabling rapid responses to potential issues.

=== Technology: Prometheus + Alertmanager

* Prometheus evaluates metrics and triggers alerts according to alerting rules.
* Example permission (Prometheus):

[source,yaml]
----
groups:
  - name: spring-alerts
    rules:
      - alert: HighErrorRate
        expr: rate(http_server_requests_seconds_count{status=~"5.."}[1m]) > 5
        for: 1m
        labels:
          severity: warning
        annotations:
          summary: "High error rate detected"
          description: "More than 5 errors per second in the last 60 seconds"
----

* Catalog entries without product assignment are hidden from every caller (fail-closed DRM) and need a data fix:

[source,yaml]
----
groups:
  - name: torg-codex-drm
    rules:
      - alert: CatalogEntriesWithoutProducts
        expr: sum by (area) (increase(torg_codex_catalog_entries_without_products_total[15m])) > 0
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "Catalog entries without product assignment in area {{ $labels.area }}"
          description: "Entries are hidden from every caller (fail-closed DRM). Fix the catalog data."
----

* Alertmanager handles routing and escalation (e.g. email, Slack).

== ✅ Summary

The observability setup is composed of the following components:

[cols="1,2",options="header"]
|===
| Component  | Technology
| Logging    | Spring Boot native structured logging + Logback + ECS JSON
| Monitoring | Spring Boot Actuator + Micrometer + Prometheus
| Alerting   | Prometheus Alert Rules + Alertmanager
|===

This setup provides deep visibility into the system’s behavior and ensures quick incident response.
