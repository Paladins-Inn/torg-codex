= Observability Concept with Spring Boot, Prometheus, and JSON Logging
include::partial$config.adoc[]

Observability refers to a system’s ability to provide insights into its internal state by exposing external outputs. It is typically built on three pillars: *Logging*, *Monitoring*, and *Alerting*.

== 🔍 Logging

Logging captures structured or unstructured information about system events. In a production-ready setup, logs are written in JSON format to facilitate automated processing and analysis.

=== Technology: Spring Boot + JSON Logging

Use Spring Boot native structured JSON logging, with Logback supplied by the
standard Boot logging starter. A separate Logstash encoder dependency or custom
encoder configuration must not be used. This replaces the former LogstashEncoder
prescription; see xref:09_architecture_decisions/017_spring-boot-structured-logging.adoc[ADR-017].

Production console configuration in `application.yaml` of the `torg-codex` module:

[source,yaml]
----
logging:
  structured:
    format:
      console: ecs
----

Production emits structured ECS JSON exclusively to standard output (`console: ecs`) with no local file logging.
Local file logging (`logging.file.name` with `logging.structured.format.file: ecs`) is restricted to the `dev`
(`logs/torg-codex.log`, overridable via `LOG_FILE`) and `test` (`target/logs/torg-codex-test.log`) profiles.
Application logging continues to use Lombok `@Slf4j` and follows the operational audience and severity rules defined in xref:08_concepts/logging-policy.adoc[Logging Policy for Operations and Support] ({adr-022}). Fields supplied through
`log.atWarn().addKeyValue(...)` must appear in emitted JSON. Verify serialized
output under production logging configuration; capturing a Logback event alone
does not prove that the configured output preserves structured fields.

* Example log output:
[source,json]
----
{
  "@timestamp": "2026-11-14T22:00:00Z",
  "log.level": "INFO",
  "log.logger": "com.example.MyService",
  "message": "User successfully created",
  "event.action": "user-created"
}
----

=== Catalog entries without product assignment (DRM)

The domain-level DRM ({adr-019}) hides catalog entries without any product assignment from every caller. Each
encounter (lists, cosm-filtered lists, single entries, embedded references and cosm reference resolution) is
reported once, without deduplication across requests, by `CatalogAccessObservabilityAdapter`:

[cols="1,3",options="header"]
|===
| Aspect | Value
| Level | `WARN`
| Message | `Catalog entry without product assignment hidden by DRM: area=…, id=…, name=…`
| Structured fields | `catalogArea` (area tag, e.g. `spell-list`), `entryId`, `entryName`
| Forbidden content | caller identity, principal, authorities, owned products, API keys
|===

`StructuredLoggingTest` parses the emitted ECS JSON of this warning under the production configuration and verifies
the structured fields and the absence of caller data.

== 📊 Monitoring

Monitoring collects metrics (e.g. latency, memory usage, throughput) to continuously observe system performance and health.

=== Technology: Spring Boot Actuator + Prometheus

* `spring-boot-starter-actuator` exposes metric names via `/actuator/metrics` and individual measurements via `/actuator/metrics/{name}`.
* `micrometer-registry-prometheus` exports metrics via `/actuator/prometheus`.
* OTLP metric, trace, and log exports are disabled by default; Prometheus pulls metrics without an OTLP collector.

=== Metrics export configuration (application.yaml)

[source,yaml]
----
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  otlp:
    metrics:
      export:
        enabled: false
  tracing:
    export:
      otlp:
        enabled: false
  logging:
    export:
      otlp:
        enabled: false
----

The application exposes additional operational endpoints in its configuration.
Metrics endpoints currently allow anonymous access; restrict access at the network or ingress boundary in production.

=== DriveThruRPG authentication and HTTP calls

Each actual DriveThruRPG HTTP call records both `drivethru.http.client.duration` (Micrometer Timer)
and `drivethru.http.client.requests` (Counter), including failures and each token-renewal retry.
Measurement surrounds the client invocation, so it includes response decoding as well as network time.
The only tags are:

* `operation`: `token-exchange`, `token-refresh`, `library-page`, `order-product`, `product`, or `publisher`.
* `outcome`: `success` or `error`, describing the HTTP client invocation (not the subsequent authentication decision).

Prometheus exports `drivethru_http_client_duration_seconds_count`, `_sum`, and `_max`, plus
`drivethru_http_client_requests_total`. No URLs, query strings, page numbers, product/customer ids,
keys, tokens or ownership lists are recorded as tags. Counts represent actual calls, not cache hits
or reuse of an already authenticated session.

The `drivethru.authentication` observation creates a `drivethru authenticate` span within the current
request trace, covering token exchange, the complete library load, and bulk publication resolution.
Its `outcome` is `success`, `rejected`, or `error`; errors contain a sanitised classification only,
never upstream exception messages/causes. The standard meter observation handler also records overall
authentication duration and count. Trace export remains disabled by default; enable the deployment's
tracing exporter and sampling to retain these spans in the tracing backend.

Before any token request, authentication writes an `INFO` event
`event.action=drivethru-auth-started` to the ECS JSON console stream (file logging is restricted to `dev`/`test` profiles), within the authentication trace scope.
It contains no principal, API key, token or owned-product list.

=== User-Page Timing Metric (`torg.codex.web.page`) and Request Boundary Logging ({adr-023}, {adr-024})

* **Single Page Timer (`torg.codex.web.page`)**:
  Enabled via `management.observations.annotations.enabled=true` (Spring Boot's auto-configured `TimedAspect`).
  All seven reader controller page handlers (`home`, `category`, `detail`, `login-view`, `login-submit`, `logout-view`, `library-reload`) carry `@Timed(value = "torg.codex.web.page", extraTags = {"page", "<value>"})`, while `LogoutTimingFilter` explicitly measures dispatched `POST /logout` submissions as `page=logout-submit` (`class=LogoutFilter`, `method=logout`).
  Every series shares the identical bounded tag-key set `{page, class, method, exception}` (`torg_codex_web_page_seconds_*` in Prometheus). Notification SSE/ack endpoints, static assets, `/actuator/**`, `/api/**`, and pre-dispatch CSRF/CORS `403` rejections are excluded. Handler-level `@Timed` measures controller execution (excluding post-handler JTE streaming; `http.server.requests` covers full HTTP lifecycle latency).
* **Request Boundary Logging (`UserRequestLoggingFilter`)**:
  Ordered after `ServerHttpObservationFilter` and before Spring Security's `FilterChainProxy`, emitting one start and one final-status completion log per logical request:
  - **User requests** (reader UI, `/admin/**`, `/api/**`, security-terminated `401`/`403`/logout): `DEBUG` `event.action=user-request-started` (`http.route` = bounded category `reader-page|admin-page|api|auth|library`) and `INFO` `event.action=user-request-completed` (`http.route` = matched Spring MVC route template or bounded fallback, `http.response.status_code`, `durationMs`, `traceId`/`spanId`).
  - **Background notification controls** (`/notifications/{stream,ack}`, `/admin/notifications/{stream,ack}`): `TRACE` start and `TRACE` completion (`AsyncListener` on SSE completion) so open browser tabs generate zero `DEBUG`/`INFO` noise.
  - **Excluded** (`/actuator/**`, `/webjars/**`, `/themes/**`, `/js/**`, `/css/**`, `/images/**`, `/favicon.ico`): zero boundary logs.
  - Raw request URIs, slugs, UUIDs, query parameters, form fields, headers, session IDs, tokens, API-key digests, and `ROLE_<codex-id>` sets are never logged. Domain outcomes (`401`, `403` teaser/CSRF, `404`) complete at `INFO`, never `WARN` or `ERROR` ({adr-022}).

Library reads initially request 200 products per page instead of 50. The API specification documents
`pageSize`, but does not state a maximum; the client honours `meta.itemsPerPage` if the server applies
a smaller size, including when pagination links are absent. Requests still omit checksums/filters and
stop at the final page. Authentication submits distinct product ids in one bulk publication query;
the query projects only publication references and avoids eager product-id collection loads.
Empty libraries require no ownership database query. Localised product ids continue to unlock the
same publication. Session reuse, renewal limits, and fail-closed behaviour on partial library failure
are unchanged.

* Prometheus is configured with a `scrape` job to periodically collect metrics:

[source,yaml]
----
scrape_configs:
  - job_name: 'spring-boot-app'
    static_configs:
      - targets: ['localhost:8080']
----

=== Catalog DRM counter

Every encounter of a catalog entry without product assignment increments the counter
`torg.codex.catalog.entries.without.products` (Prometheus:
`torg_codex_catalog_entries_without_products_total`). Its only tag is `area` (one of the 14 catalog area tags),
keeping the cardinality bounded; entry ids, names and caller data are never used as tags. The counter is
monotonic per application instance: use its increase over time, not its absolute value, to detect current data gaps.

=== Catalog Usage & Roll-Up Counters

Channel-agnostic catalog usage across both the Web UI and `/api/*` REST endpoints is reported by the core query
services through `CatalogUsageObserver` and exported by `CatalogUsageObservabilityAdapter` without recording
caller identity, credentials, or `ROLE_<codex-id>` authorities:

* **Granular counters (4 meter families)**:
- `torg.codex.catalog.usage.category\{category}` — per-category reads across all 17 `CatalogArea` slugs.
- `torg.codex.catalog.usage.cosm\{cosm}` — accesses and validated cosm filters per known cosm slug.
- `torg.codex.catalog.usage.grouping\{dimension,group}` — accesses and validated facet filters across known Perk Groups, Spell/Miracle/Power Lists, Tags, Item/Vehicle Types, Clearances, and Races.
- `torg.codex.catalog.usage.detail\{category,entry,outcome}` — single-entry lookups by canonical slug across `drm-granted`, `public-reference`, `teaser`, and `not-found` (using the bounded sentinel `entry="_not_found_"` so unknown URLs never create unbounded time series).
* **Outcome roll-up counters (4 untagged totals)**:
  - `torg.codex.catalog.usage.outcome.drm.granted`
  - `torg.codex.catalog.usage.outcome.public.reference`
  - `torg.codex.catalog.usage.outcome.teaser`
  - `torg.codex.catalog.usage.outcome.not.found`
* **Metric-family roll-up counters (4 untagged totals)**:
  - `torg.codex.catalog.usage.family.category`
  - `torg.codex.catalog.usage.family.cosm`
  - `torg.codex.catalog.usage.family.grouping`
  - `torg.codex.catalog.usage.family.detail`

== 🚨 Alerting

Alerting generates notifications based on defined thresholds in metrics, enabling rapid responses to potential issues.

=== Technology: Prometheus + Alertmanager

* Prometheus evaluates metrics and triggers alerts according to alerting rules.
* Example permission (Prometheus):

[source,yaml]
----
groups:
  - name: spring-alerts
    rules:
      - alert: HighErrorRate
        expr: rate(http_server_requests_seconds_count{status=~"5.."}[1m]) > 5
        for: 1m
        labels:
          severity: warning
        annotations:
          summary: "High error rate detected"
          description: "More than 5 errors per second in the last 60 seconds"
----

* Catalog entries without product assignment are hidden from every caller (fail-closed DRM) and need a data fix:

[source,yaml]
----
groups:
  - name: torg-codex-drm
    rules:
      - alert: CatalogEntriesWithoutProducts
        expr: sum by (area) (increase(torg_codex_catalog_entries_without_products_total[15m])) > 0
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "Catalog entries without product assignment in area {{ $labels.area }}"
          description: "Entries are hidden from every caller (fail-closed DRM). Fix the catalog data."
----

* Alertmanager handles routing and escalation (e.g. email, Slack).

== ✅ Summary

The observability setup is composed of the following components:

[cols="1,2",options="header"]
|===
| Component  | Technology
| Logging    | Spring Boot native structured logging + Logback + ECS JSON
| Monitoring | Spring Boot Actuator + Micrometer + Prometheus
| Alerting   | Prometheus Alert Rules + Alertmanager
|===

This setup provides deep visibility into the system’s behavior and ensures quick incident response.
