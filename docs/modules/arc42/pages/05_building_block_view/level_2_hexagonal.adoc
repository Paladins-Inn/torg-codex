= Level 2: Hexagonal Module Structure
include::partial$config.adoc[]

Following the architecture migration described in
link:https://github.com/Paladins-Inn/torg-codex/tree/main/specs/architecture-migration[
`specs/architecture-migration/`], {system} is split into four Maven reactor modules that
enforce a strict, one-directional hexagonal (ports-and-adapters) dependency chain.

== Dependency direction

`torg-codex` and `torg-codex-data` both depend on `torg-codex-application`, which depends on
`torg-codex-domain`. `torg-codex-domain` depends on nothing else in the reactor. This is the
one direction in which compilation dependencies are allowed to flow; the reverse direction
(e.g. `torg-codex-domain` depending on `torg-codex-data`) is impossible because
`torg-codex-domain`'s own `pom.xml` declares no such dependency, and is additionally checked
by `ModuleBoundaryArchitectureTest`.

== Continuous enforcement

An ArchUnit-based test suite under
`torg-codex/src/test/java/de/paladinsinn/torg/codex/architecture/` runs as part of the
standard `mvn test`/`mvn verify` lifecycle (it cannot be skipped or excluded to pass a task)
and enforces:

[cols="<.<4h,<.<8a",options="header",frame="topbot",grid="rows"]
|===
| Test | Enforces

| `DomainPurityArchitectureTest`
| `torg-codex-domain` imports no `org.springframework..`, `jakarta.persistence..`, or
  `org.hibernate..` class.

| `ApplicationPurityArchitectureTest`
| `torg-codex-application` imports no Spring/JPA/Hibernate class and declares no
  `@Transactional` annotation.

| `TransactionBoundaryArchitectureTest`
| Neither `torg-codex-application` nor `torg-codex-domain` declares `@Transactional` at the
  class or method level; the annotation lives only at the inbound-adapter boundary
  (`torg-codex`'s REST controllers).

| `AdapterConventionArchitectureTest`
| REST controllers live under `api.controller..`; classes named `*Adapter` in
  `torg-codex-data` live under `data.adapter.out..`; the DriveThruRPG HTTP adapter, the
  domain-event bridge adapter, and all 17 catalog-area controllers are present at their
  expected locations.

| `ModuleBoundaryArchitectureTest`
| The reactor-wide module dependency direction described above.

| `FreezeListEnforcementArchitectureTest` / `FreezeListFormatTest`
| The version-controlled freeze list
  (`specs/architecture-migration/freeze-list.md`) that backs every rule above tolerates only
  its explicitly listed, fully-documented, rationale-backed exceptions — never an unlisted
  violation — and is itself well-formed.
|===

As of the completion of the architecture migration, the freeze list holds a single row,
`FL-007`, documenting a permanent spec-level (not code-level) accepted deviation regarding
AMQP messaging (see xref:09_architecture_decisions/003_messaging-rabbitmq.adoc[ADR-003] and
`specs/architecture-migration/spec.md`'s FR-010 deviation note) — there is no outstanding,
unresolved architecture-boundary violation anywhere in the codebase.
