# Quickstart: Validating the Unified Censoring Authorization Fix

This guide describes how to run/validate this feature once implemented. It does not contain
implementation code — see `data-model.md` and `contracts/` for the design, and `tasks.md`
(generated by `/speckit.tasks`) for the implementation steps.

## Prerequisites

- **JDK 25** (verified working: Eclipse Temurin 25.0.3 at `/usr/lib/jvm/temurin-25-jdk-amd64`).
  Set `JAVA_HOME` accordingly, e.g.:
  ```bash
  export JAVA_HOME=/usr/lib/jvm/temurin-25-jdk-amd64
  export PATH="$JAVA_HOME/bin:$PATH"
  ```
- **Docker** (or a compatible container runtime) available for Testcontainers-backed integration
  tests (`*IT`, `@SpringBootTest` classes under `torg-codex/src/test/java`) run by
  `./mvnw clean verify`.
- Run all commands from the repository root: `/home/klenkes74/Documents/github/paladins-inn/torg-codex`.

## Step 1 — Confirm the baseline still builds (before any change)

```bash
./mvnw -o test-compile
```
Expected: `BUILD SUCCESS` (already verified during planning — offline compile is clean).

## Step 2 — Unit-level validation: `ProductOwnershipResolver`

Once implemented, run just the new/ported unit test in isolation:

```bash
./mvnw -pl torg-codex test -Dtest=ProductOwnershipResolverTest
```

Expected outcomes (per `contracts/product-ownership-resolver.md`'s Test Contract):
- No authentication → resolves to an empty set.
- Anonymous authentication with `ROLE_ANONYMOUS` → resolves to `{"ANONYMOUS"}`.
- Authenticated principal (any type, e.g. a plain Spring Security `User`) carrying
  `ROLE_core-rulebook` + `ROLE_sourcebook-aysle` → resolves to
  `{"core-rulebook", "sourcebook-aysle"}` — this is the specific case that was broken before this
  feature (a non-`DriveThruUserDetails` principal was previously ignored entirely).
- A non-`ROLE_`-prefixed authority (e.g. `SCOPE_read`) is excluded from the result.

## Step 3 — Integration-level validation: live anonymous-vs-owner difference

Run the new differential test plus the existing characterization suite:

```bash
./mvnw -pl torg-codex verify -Dit.test=CensoringDifferentialTest,CharacterizationReplayTest
```

Expected outcomes (per spec User Story 1 Acceptance Scenarios 1–3, FR-008, SC-001):
- A request with `ROLE_sourcebook-aysle` against `GET /api/cosms/6cf031c3-ab0a-4d12-9173-91d74f7c809f`
  (the Aysle cosm) returns a `worldLaws` value containing the owner-only content from the
  `<IF:sourcebook-aysle>...</IF>` block and **not** the upsell content from
  `<IF:!sourcebook-aysle>...</IF>`.
- An anonymous request against the same endpoint returns the opposite: the upsell content, not
  the owner-only content.
- The two response bodies **differ** — this is the core regression-detection assertion that must
  fail loudly if the single-mechanism consolidation is ever reverted.

## Step 4 — Regenerate characterization fixtures and confirm they now genuinely differ

```bash
./mvnw -pl torg-codex test -Dtest=CharacterizationFixtureCaptureTest -Dcharacterization.capture=true
git diff --stat torg-codex/src/test/resources/characterization/
```

Expected outcome: `torg-codex/src/test/resources/characterization/cosms/owner-detail.json` and
`anonymous-detail.json` (and possibly other areas whose sampled "DRM-sensitive" id changes) are
no longer byte-identical to each other — confirms `CharacterizationFixtureCaptureTest`'s
`findDrmSensitiveId()` probe now actually finds a differing sample, where before the fix it
always fell through to an arbitrary first entity (see `research.md` Decision 5). Commit the
regenerated fixtures so `CharacterizationReplayTest` locks in the corrected behavior for future
regressions.

## Step 5 — Confirm no regression for non-gated content

```bash
git diff --stat torg-codex/src/test/resources/characterization/ | grep -v cosms
```
Expected: no other catalog area's fixtures change unless their sampled detail id also happens to
newly become a true DRM-sensitive id (unlikely but not precluded); any *unexpected* diff here
would indicate an FR-009 regression and must be investigated before proceeding.

## Manual smoke test (optional, human-readable sanity check)

If running the application locally with a test/dev profile:

```bash
# Anonymous
curl -s http://localhost:8080/api/cosms/6cf031c3-ab0a-4d12-9173-91d74f7c809f | jq -r .worldLaws
# Authenticated as an Aysle owner (however the local/dev security setup allows asserting
# ROLE_sourcebook-aysle, e.g. a dev-only Spring profile or a valid DriveThruRPG API key for a
# test account that owns the Aysle sourcebook)
curl -s -H "Authorization: ApiKey <a-real-test-key-owning-sourcebook-aysle>" \
  http://localhost:8080/api/cosms/6cf031c3-ab0a-4d12-9173-91d74f7c809f | jq -r .worldLaws
```
Expected: the two `worldLaws` outputs visibly differ — the anonymous one shows the "you need this
book" style upsell notice; the authenticated one shows the real owner-only world-law content.
