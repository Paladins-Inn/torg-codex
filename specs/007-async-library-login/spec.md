# Feature Specification: Asynchronous Library Login, User Notifications, Caching, and Request Observability

**Feature Branch**: `007-async-library-login`

**Created**: 2026-11-16

**Status**: Draft

**Input**: User description: "make the loading of drivethru library during login an asynchronous projcess. after loading the token the loading of the purchased publications should run in parallel. Introduce a way to send notifcations to the user asynchronously. The notifications should be toast components. an information should be sent when the loading starts with a note, that the user is logged in but it could take several minutes till the user gets access to all his publications due to long running requests to drivethrurpg. Every batch loaded should be added imediately to the user. After loading finished a notification should be sent again. If loading or authenticaiton fails a notification is to be sent, too. ## Clarifications

### Session 2026-11-16

- Q: How generic should the asynchronous toast notification system be, and which UI surfaces must it support? → A: The notification system MUST be generic and domain-agnostic so any feature or background workflow can emit notifications (with DriveThruRPG login/library sync as its first producer), shared across both the public reader UI and the `/admin` UI layout shell with each layout styling toast components in its own isolated visual theme.
- Q: How should generic toast notifications handle dismissal across severity levels? → A: Informational (`info`) and completion (`success`) toasts auto-dismiss after a short delay while remaining manually closeable; `warning` and `error` toasts stay visible until explicitly closed by the user.
- Q: Which toast notification(s) should be shown when a user signs in with an API key whose library is already in the memory cache? → A: Skip the multi-minute loading warning toast on a cache hit and send a single `success` confirmation toast stating that the user is signed in and their publications are ready; reserve the start warning + completion toast pair for uncached background loads.
- Q: While a user stays on an open reader page as background batches and completion unlock new publications, how should the open page's main content behave? → A: Keep the currently open page content stable (no automatic mid-reading page replacement) while offering an optional one-click reload action on the completion toast; newly unlocked publications appear immediately on any navigation, filter interaction, or reload.
- Q: Because signing out must not clear the in-memory API-key library cache, how should a user who just bought a new publication on DriveThruRPG unlock it? → A: Retain cached API-key library entries with a configurable 12-hour default TTL and provide signed-in users an explicit option to manually reload their library asynchronously from DriveThruRPG, refreshing the cached entry once the full reload succeeds.
- Q: How should the required Architecture Decision Record (`ADR-023`) approval gate be sequenced relative to implementation? → A: Draft `ADR-023` with status `Proposed` during initial setup and require explicit maintainer review and acceptance at the pre-merge gate after implementation completes before merging.
- Q: How should user-page timing metrics cover full page rendering and sign-out alongside declarative handler annotations? → A: Record a single user-page timing metric using declarative handler-level timing across page handlers plus explicit timing only on sign-out submission where declarative handler timing cannot attach (without introducing a second separate handler/page metric split).
- Q: Should automated background toast-stream and acknowledgment requests emit DEBUG start and INFO completion user-request logs? → A: Exclude automated background toast-stream (SSE) and acknowledgment requests from `DEBUG` start and `INFO` completion user-request logs, and emit `TRACE` logs for them instead.
- Q: How should manual library reload identify the user's cache entry and behave if their upstream DriveThruRPG token can no longer be renewed? → A: Retain only a non-reversible API-key digest in the active session (never the cleartext API key) to key library cache reads/updates; if upstream DriveThruRPG token renewal fails during a manual reload, keep existing session and cached entitlements intact and display a sticky `error` toast prompting the user to sign in again.
- Q: How should state-changing session endpoints (manual library reload and toast acknowledgment across reader and `/admin` surfaces) protect against cross-site requests? → A: Enforce standard framework-managed CORS restrictions and anti-forgery (CSRF) tokens across all reader and `/admin` HTML forms and dynamic UI `POST` requests (including sign-in, sign-out, manual library reload, and toast acknowledgment), rejecting disallowed cross-origin or missing/invalid-token requests with `403 Forbidden` while keeping stateless catalog REST API endpoints exempt from browser CSRF tokens.
- Q: Should browser toast notifications rely on periodic HTTP polling or event-driven push, and which recipient scopes must event-driven notifications support? → A: Replace periodic browser polling with Spring Event-driven messaging (`ApplicationEventPublisher` / `@EventListener`) pushing server-rendered toast fragments over Server-Sent Events (`SseEmitter` / `EventSource`), supporting events targeted either to a single current session or broadcast to all currently logged-in users (prepared for the `/admin` frontend and unused in production workflows today), documented in dedicated `ADR-024` alongside `ADR-023`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Sign In Immediately While Purchased Publications Unlock Incrementally (Priority: P1)

A player or game master with a large DriveThruRPG library signs in on the Torg Codex Login page using their DriveThruRPG API key. Instead of waiting minutes on a blocked login screen while their entire multi-page purchase history is fetched from DriveThruRPG, Torg Codex validates their API key by obtaining an authentication token, immediately signs them in, and redirects them into the codex with free-tier (`core-rulebook`) content available right away. In parallel with their browsing session, Torg Codex retrieves their purchased publications asynchronously in the background. Each batch of library items retrieved from DriveThruRPG is immediately mapped to Torg Eternity publications and added to the user's active session entitlements on the fly, unlocking additional sourcebook entries and gated passages progressively until the full library is loaded.

**Why this priority**: Eliminating multi-minute login stalls is the core user pain point motivating this feature, turning an unresponsive sign-in wait into immediate codex access with progressive unlocking.

**Independent Test**: Sign in with a valid API key whose DriveThruRPG library spans multiple slow batches; verify that login completes and redirects immediately after token acquisition (without waiting for the first slow library batch), that free-tier entries are immediately browseable, and that as each batch completes in the background, publications in that batch become accessible on subsequent views before later batches finish.

**Acceptance Scenarios**:

1. **Given** a visitor submits a valid DriveThruRPG API key whose library takes several batches and multiple seconds per batch to retrieve, **When** token validation succeeds, **Then** the user is immediately signed in and redirected to the codex without waiting for DriveThruRPG library batches to finish loading.
2. **Given** background library loading is in progress across multiple batches and Batch 1 contains `sourcebook-aysle` while Batch 2 is still pending, **When** Batch 1 finishes loading and the user views or refreshes a category table, landing page, or `sourcebook-aysle` entry detail, **Then** `sourcebook-aysle` entries and `<IF:…>` gated passages are already unlocked and visible while Batch 2 continues loading in parallel.
3. **Given** Batch 1 already unlocked `sourcebook-aysle` for the active session, **When** Batch 2 subsequently finishes and unlocks a second publication, **Then** the user's active session entitlements contain the union of free-tier `core-rulebook`, `sourcebook-aysle`, and the newly loaded publication without revoking earlier batches.
4. **Given** any catalog view (landing page, category table, filtered results, embedded list, or single-element detail/teaser), **When** incremental batches update the user's entitlements, **Then** all DRM checks and gated-text censoring continue to flow exclusively through the single unified product-ownership authorization mechanism.

### User Story 2 - Receive Asynchronous Toast Notifications for Authentication and Library Status (Priority: P1)

As a user signs in and browses Torg Codex while their library synchronizes in the background, the interface keeps them clearly informed via non-blocking toast notification components delivered asynchronously. Right when library loading begins, an informational toast confirms that the user is signed in and explains that it could take several minutes until they gain access to all of their purchased publications due to long-running requests to DriveThruRPG. Once every batch of their library has finished loading, a completion toast notifies them that all purchased publications are now available. If either initial authentication or background library loading fails, an error toast notifies the user of the failure so they are never left wondering why publications are missing.

**Why this priority**: Because sign-in now returns before all purchased books are unlocked, clear asynchronous user feedback is essential so users understand why some owned sourcebooks are not yet visible during the first moments or minutes after login and know when synchronization completes or fails.

**Independent Test**: Sign in with a valid API key and observe the start toast immediately on the landing page, keep the page open (or navigate between pages) until background synchronization finishes and verify the completion toast appears asynchronously without requiring a manual page reload; separately trigger an invalid-credential login failure and a mid-stream DriveThruRPG library failure and verify an error toast appears in each case.

**Acceptance Scenarios**:

1. **Given** a user submits a valid API key and background library loading starts, **When** the user lands on the codex page following login, **Then** a non-blocking informational toast notification is displayed stating that the user is signed in and noting that it could take several minutes until access to all purchased publications is available due to long-running DriveThruRPG requests.
2. **Given** a signed-in user has a codex page open while an uncached background library load completes, **When** the final batch finishes and all purchased publications have been applied to the user, **Then** the open page stays undisturbed while a completion toast notification is delivered asynchronously confirming that library loading has finished and offering a one-click reload action for the current view.
3. **Given** a visitor submits invalid credentials or DriveThruRPG token validation fails during sign-in, **When** the login attempt fails, **Then** the visitor is not signed in and receives an error toast notification clearly reporting that authentication failed without exposing credentials or technical internals.
4. **Given** a signed-in user's background library loading encounters an unrecoverable DriveThruRPG failure after token validation, **When** background loading aborts, **Then** an error toast notification is delivered asynchronously to the user explaining that loading purchased publications from DriveThruRPG failed.

### User Story 3 - Reuse Cached Library Results Across Logins Without Logout Eviction (Priority: P2)

When a user's DriveThruRPG library has already been retrieved for a given API key, Torg Codex caches that complete library result in volatile memory associated with that API key across all library loadings for a 12-hour default retention window. If the user signs out and later signs back in with the same API key—or triggers another library lookup while the cached entry is still valid—the system reuses the cached library data instead of calling DriveThruRPG's slow library endpoint again. Signing out still immediately clears the user's active browser session so the signed-out browser reverts to free-tier (`core-rulebook`) access, while preserving the underlying in-memory library cache entry. If a signed-in user purchases a new publication on DriveThruRPG before the 12-hour cache expires, they can manually trigger an asynchronous library reload from DriveThruRPG to refresh their cached library and unlock the new publication.

**Why this priority**: Caching complete library lookups per API key across session boundaries eliminates repeated multi-minute external calls for returning users and repeated API-key requests while keeping logout session security intact.

**Independent Test**: Complete a full library load for an API key, sign out (verifying the browser immediately reverts to free-tier visibility only), sign back in with the same API key, and verify that zero external DriveThruRPG library requests are issued while all owned publications are restored immediately from cache.

**Acceptance Scenarios**:

1. **Given** a complete DriveThruRPG library load has succeeded for a specific API key and remains in the volatile memory cache, **When** a subsequent library load is requested for that same API key, **Then** the cached library result is used and zero external DriveThruRPG library calls are made.
2. **Given** a signed-in user whose library result is stored in the memory cache selects Sign Out, **When** sign-out completes, **Then** the user's browser session immediately reverts to anonymous free-tier (`core-rulebook`) access, **And** the cached library result for that API key is retained in memory rather than invalidated.
3. **Given** a user signed out in Scenario 2 while their library result remained in cache, **When** they sign in again with the same valid API key, **Then** their purchased publications are unlocked immediately from the cached library result without re-querying the external DriveThruRPG library endpoint, and a single ready confirmation toast is displayed without the multi-minute loading warning toast.
4. **Given** a library load fails part-way through due to an upstream DriveThruRPG error, **When** the failed load terminates, **Then** the incomplete result is not stored in the cache, and a subsequent library load for that API key performs a fresh retrieval from DriveThruRPG.
5. **Given** a signed-in user purchases a new Torg Eternity publication on DriveThruRPG before their 12-hour cached library entry expires, **When** they activate the manual library reload option, **Then** Torg Codex bypasses the cached entry, reloads their library asynchronously from DriveThruRPG in the background (with incremental batch updates and start/completion/failure toasts), and replaces the cached entry once the full reload completes.

### User Story 4 - Measure Every User Page and Log Request Boundaries (Priority: P2)

Operations and support engineers monitoring Torg Codex in production can observe the responsiveness of every user-facing page through timing metrics and trace request execution boundaries through structured operational logs. Every user page and interactive view endpoint records duration and count metrics, and every incoming user request emits a `DEBUG` log entry when processing starts and an `INFO` log entry when processing finishes, adhering strictly to the system's operations-first logging and data-protection rules.

**Why this priority**: Quantitative per-page latency metrics and consistent request start/end log boundaries give Operations immediate visibility into slow user-facing views and request lifecycles without requiring ad-hoc code changes.

**Independent Test**: Exercise every user-facing reader page (landing page, category listing and filter update, accessible entry detail, purchase teaser, not-found entry, login page, login submission, and logout), inspect published operational metrics to confirm duration and count recordings exist for each page, and inspect structured logs with `DEBUG` enabled to confirm one `DEBUG` start record and one `INFO` completion record per user request with zero sensitive data.

**Acceptance Scenarios**:

1. **Given** visitors access any user-facing reader page (landing, category view, filtered table view, element detail/teaser/not-found view, login, manual library reload, and logout), **When** each page request is handled, **Then** a single user-page timing metric records both the invocation count and execution duration for that page using bounded, low-cardinality labels (via declarative handler-level timing on page handlers and explicit timing only on sign-out submission).
2. **Given** `DEBUG` logging is enabled for request boundary diagnostics, **When** any user request arrives and completes, **Then** exactly one structured `DEBUG` log entry is emitted at request start and one structured `INFO` log entry is emitted at request completion.
3. **Given** default production `INFO` logging is active (`DEBUG` disabled), **When** a user request arrives and completes (including domain outcomes such as invalid login credentials, unowned-entry teasers, or unknown entry slugs), **Then** the `INFO` request-completion entry is emitted without emitting `WARN` or `ERROR` for domain outcomes, and zero logs or metrics contain API keys, tokens, or caller owned-product sets.

### Edge Cases

- **Post-login redirect (`Login` → `Home`) and rapid page navigation**: Toast notifications queued at login start, completion, or failure remain buffered for the user's session until actually delivered to the browser UI, so redirects or clicking between categories never silently drop a notification and delivered notifications are not re-shown endlessly on every subsequent page load.
- **Partial batch success followed by mid-stream DriveThruRPG error**: Batches already retrieved and verified during the active session remain unlocked for that session, unretrieved batches remain locked (fail-closed), an asynchronous failure toast informs the user that library synchronization did not complete, and the partial result is never cached.
- **Expired upstream DriveThruRPG token during manual library reload**: Because the active session retains only a non-reversible API-key digest rather than the cleartext API key, if the session's DriveThruRPG token and refresh token have expired when the user triggers a manual reload, existing session entitlements and any prior valid cached library entry remain intact while a sticky `error` toast prompts the user to sign in again.
- **Cross-site or tokenless state-changing browser `POST` requests**: Disallowed cross-origin requests (CORS) or submissions to sign-in, sign-out, manual library reload, or toast acknowledgment without a valid anti-forgery (CSRF) token are rejected (`403 Forbidden`) without mutating session, cache, or notification state, while stateless `/api/**` requests using an `Authorization: ApiKey <key>` header remain exempt from browser CSRF tokens.
- **Sign-out while background library loading is still running**: The signed-out session immediately loses all non-free publication entitlements and receives no further session updates or toasts from the prior login's background task.
- **Duplicate or concurrent sign-in submissions in the same session**: Starting a new sign-in cleanly supersedes or coordinates with any in-flight session synchronization so duplicate toasts and conflicting entitlement updates do not occur.
- **User with an empty DriveThruRPG library or zero Torg Eternity publications**: Sign-in succeeds, an uncached load still delivers start and completion toast notifications cleanly (while a cached hit shows the single ready toast), the empty library result is cached for that API key, and the user retains free-tier (`core-rulebook`) access.
- **Stateless API requests using an `ApiKey` header**: Non-browser stateless API calls continue to return complete ownership-filtered responses within their single request lifecycle while sharing the API-key library cache so repeated calls avoid external DriveThruRPG library fetches.
- **High-cardinality paths and query parameters in metrics and logs**: Arbitrary URL slugs, UUIDs, search queries, and credentials never create unbounded metric tag values and never expose secrets in request start/end log entries.
- **Non-user infrastructure and background-notification traffic**: Automated health/metrics probes and static asset file fetches (stylesheets, scripts, icons) do not emit user-request boundary logs or user-page timing metrics, while automated background toast SSE-stream and acknowledgment requests emit `TRACE` logs rather than `DEBUG`/`INFO` user-request logs so open tabs do not pollute operational logs.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: During reader sign-in, the system MUST synchronously validate the submitted DriveThruRPG API key by obtaining an authentication token before establishing an authenticated session; if token validation fails due to invalid credentials or upstream unavailability, the system MUST reject sign-in immediately without starting background library loading.
- **FR-002**: Immediately upon successful DriveThruRPG token acquisition during reader sign-in, the system MUST establish the user's authenticated session (initially granting free-tier `core-rulebook` access, plus any already-cached publications if immediately available) and complete the sign-in response without waiting for uncached DriveThruRPG library requests to finish.
- **FR-003**: Following token acquisition on reader sign-in, retrieval of the user's purchased publications MUST execute asynchronously in parallel with the user's active browsing session.
- **FR-004**: As each batch of DriveThruRPG library items is retrieved and resolved to catalog publications, the system MUST immediately add those publications to the signed-in user's active session entitlements before remaining batches finish, preserving all previously granted entitlements in that session and enforcing access exclusively through the single unified product-ownership mechanism.
- **FR-005**: The system MUST provide a generic, domain-agnostic asynchronous user notification service and UI delivery mechanism usable by any application feature or background workflow across both the reader UI and `/admin` UI layout shells (with each layout shell styling toast components in its own isolated theme), supporting `info`, `success`, `warning`, and `error` severities (with auto-dismiss for `info`/`success` and sticky manual-close behavior for `warning`/`error`) plus an optional interactive action per toast, rendering notifications without requiring manual page reloads when a page is open, and preserving undelivered session notifications across page redirects and navigation until displayed once.
- **FR-006**: When an uncached asynchronous library load begins after sign-in, the system MUST send an `info` toast notification to the user stating that they are signed in and noting that it could take several minutes until they receive access to all of their purchased publications due to long-running requests to DriveThruRPG; when sign-in resolves the library immediately from the memory cache, the system MUST omit that multi-minute warning toast and instead send a single `success` toast confirming that the user is signed in and their publications are ready.
- **FR-007**: When an uncached background library load finishes successfully for the signed-in user, the system MUST keep any currently open reading view undisturbed and send an asynchronous `success` completion toast notification informing the user that all of their purchased publications have been loaded and offering a one-click action to reload the current view.
- **FR-008**: If reader authentication fails during sign-in (invalid API key or token-validation service failure), the system MUST display an error toast notification informing the user that authentication failed, without exposing credentials or raw upstream error payloads.
- **FR-009**: If background library loading fails before all batches are retrieved, the system MUST send an asynchronous error toast notification informing the user that loading their DriveThruRPG library failed, retain any publication batches already verified during that session, and leave unretrieved batches locked (fail-closed).
- **FR-010**: The system MUST cache complete DriveThruRPG library lookup results in volatile memory across all library loadings with a configurable time-to-live defaulting to 12 hours, keyed by a deterministic non-reversible digest of the caller's normalized API key (so cleartext API keys are never retained in cache keys or session state, nor exposed in logs, metrics, or diagnostic views) and preventing external DriveThruRPG library requests whenever a valid cache entry exists for that API key.
- **FR-011**: User sign-out MUST terminate the user's active browser session entitlements immediately (reverting the browser session to free-tier `core-rulebook` visibility and detaching any in-flight session synchronization) and MUST NOT evict or invalidate cached DriveThruRPG library results associated with that API key.
- **FR-012**: Failed, aborted, or incomplete DriveThruRPG library loadings MUST NOT populate or overwrite valid entries in the API-key library cache.
- **FR-013**: Stateless single-request API-key authentication on catalog REST endpoints MUST preserve backward-compatible full ownership resolution per request while using the shared API-key library cache to bypass external DriveThruRPG library calls on cache hits.
- **FR-014**: Every user-facing reader page and interactive UI view endpoint (including landing, category listing and filtered table updates, entry detail/teaser/not-found views, login page and submission, manual library reload, and logout view and submission) MUST record execution duration and invocation count under a single user-page timing metric with strictly bounded, low-cardinality metric attributes, using declarative handler-level timing across page handlers and explicit timing only on sign-out submission where handler-level timing cannot attach.
- **FR-015**: Every incoming user request (across reader web UI views and catalog API endpoints, excluding static asset files, infrastructure health/scrape endpoints, and automated background toast-stream/acknowledgment requests) MUST emit a structured operational `DEBUG` log entry at request start and a structured operational `INFO` log entry at request completion; automated background toast SSE-stream and acknowledgment requests MUST emit structured `TRACE` log entries instead.
- **FR-016**: Request start (`DEBUG`), request completion (`INFO`), background toast-stream/acknowledgment (`TRACE`), authentication, and background synchronization logs and metrics MUST strictly comply with the Operations-First Logging Policy and data-protection rules: never logging API keys, tokens, session secrets, or caller owned-product sets at any severity level, and logging user/domain outcomes (invalid credentials, purchase teasers, not-found lookups) at `INFO` rather than `WARN` or `ERROR`.
- **FR-017**: Automated tests MUST verify immediate post-token login response, parallel background batch loading with incremental entitlement unlocking, generic event-driven asynchronous toast notifications pushed via Spring Events + SSE across severities and dismissal modes (uncached start/completion with reload action, cache-hit single ready toast, authentication failure, and library-load failure), 12-hour API-key library cache hits across logout/re-login without external library calls, manual asynchronous library reload (including expired-token handling), non-caching of partial failures, CORS and CSRF protection on state-changing UI `POST` requests, per-page timing metrics, and `DEBUG` start / `INFO` end user-request logging (plus `TRACE` toast-stream/acknowledgment logging) without credential leakage.
- **FR-018**: The reader UI MUST provide signed-in users an explicit option to manually reload their purchased library asynchronously from DriveThruRPG using the session's non-reversible API-key digest (without re-submitting or storing the cleartext API key in session state), bypassing the existing cached entry, applying incremental batches and lifecycle toasts per `FR-004` and `FR-006`–`FR-009`, replacing the cached entry only upon full reload success (`FR-012`), and—if the session's upstream DriveThruRPG token can no longer be renewed—preserving current session and cached entitlements while displaying a sticky `error` toast prompting the user to sign in again.
- **FR-019**: Browser UI endpoints across both the reader UI and `/admin` UI surfaces MUST enforce restrictive cross-origin resource sharing (CORS) rules and require valid anti-forgery (CSRF) tokens on all HTML form submissions and dynamic UI `POST` requests (including sign-in submission, sign-out submission, manual library reload, and notification acknowledgment), rejecting disallowed cross-origin or missing/invalid-token requests with `403 Forbidden` while keeping stateless catalog REST API endpoints exempt from browser CSRF tokens.

### Key Entities *(include if feature involves data)*

- **Background Library Synchronization**: An asynchronous session-bound workflow started upon uncached sign-in or manual library reload that retrieves a user's DriveThruRPG library in batches, incrementally expands the session's owned-publication entitlements after each batch, and emits lifecycle notifications through the generic user notification service.
- **User Notification Toast**: A generic, domain-agnostic transient user message usable by any feature or workflow across reader and `/admin` layouts, carrying a severity (`info`, `success`, `warning`, or `error`—with auto-dismiss for `info`/`success` and sticky manual-close behavior for `warning`/`error`), concise summary text, an optional interactive action (such as reloading the current page), and delivery state scoped to the user's browser session so it is displayed once as a toast component either immediately on an open page or upon the next page render following a redirect.
- **API-Key Library Cache Entry**: A volatile in-memory record associating an API key's credential-safe lookup key with the complete resolved DriveThruRPG library result (owned product identifiers and associated customer identifier where present), retained across user logouts for a configurable 12-hour default TTL until expiration, memory eviction, or replacement by a completed manual library reload.
- **User Request Telemetry Record**: The operational observability footprint of a user request, consisting of bounded per-page duration/count metrics plus paired structured log events (`DEBUG` on request entry and `INFO` on request completion with matched route, status outcome, and elapsed time).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: When DriveThruRPG token validation responds within normal latency (< 2 seconds) while library retrieval takes 30+ seconds across multiple batches, 100% of reader sign-ins complete login and render the destination codex page within 3 seconds of form submission without waiting for library batches.
- **SC-002**: During a multi-batch background library load, 100% of catalog publications resolved in a completed batch become accessible to the signed-in user within 1 second of that batch finishing, even while subsequent batches are still in flight.
- **SC-003**: Users receive 100% of applicable generic toast notifications—uncached start `info` toast (with the multi-minute DriveThruRPG loading note), uncached completion `success` toast (with one-click view reload), cache-hit single ready `success` toast, and sticky `error` toasts for authentication or library failures—within 5 seconds of each event occurring while viewing a page, with 0 notifications lost across redirects and 0 unsolicited mid-reading page replacements.
- **SC-004**: Repeated library loadings for an API key within the 12-hour default in-memory cache TTL—including after signing out and signing back in—issue 0 external DriveThruRPG library requests and unlock 100% of cached publications within 1 second of token validation, while sign-out revokes 100% of non-free session access immediately and manual library reload refreshes newly purchased publications asynchronously without server restart.
- **SC-005**: 100% of user-facing reader page endpoints expose measurable invocation count and duration metrics with bounded label cardinality, regardless of how many distinct entry slugs, UUIDs, or search terms users request.
- **SC-006**: 100% of in-scope user requests emit one structured `DEBUG` log record at request start (when `DEBUG` is enabled) and one structured `INFO` log record at request completion (while automated background toast SSE-stream and acknowledgment requests emit `TRACE` records rather than `DEBUG`/`INFO`), with 0 occurrences of raw API keys, tokens, or caller owned-product sets in any log entry or metric tag, and 0 `WARN`/`ERROR` log entries triggered by invalid credentials, purchase teasers, or missing entry URLs.

## Assumptions

- Volatile in-memory caching uses bounded memory capacity and a configurable time-to-live retention window (defaulting to 12 hours) so memory growth remains bounded while signed-in users can also trigger an asynchronous manual library reload at any time; persistent or distributed cache infrastructure is out of scope.
- Cache lookup keys represent the submitted API key deterministically without exposing cleartext API keys in operational logs, error messages, or monitoring endpoints; DriveThruRPG token validation still verifies that a submitted API key is valid when establishing a new session.
- Asynchronous browser toast delivery operates within the existing self-contained web application without requiring external notification infrastructure or third-party push services, sharing the generic notification model across both the reader UI and `/admin` UI layout shells while keeping each surface's visual theme stylesheet isolated.
- Stateless external REST requests authenticating via the `Authorization: ApiKey <key>` header require complete product entitlements within that single request-response cycle and therefore await full library resolution on a cache miss while reusing the shared API-key library cache on subsequent requests.
- "User requests" for `DEBUG` start and `INFO` completion logging cover all user-facing reader UI page/fragment requests and catalog REST API requests, excluding static asset requests (stylesheets, scripts, fonts, icons) and operational actuator health/metrics scrape endpoints, while automated background toast SSE-stream and acknowledgment requests are logged at `TRACE` level so notification transport does not generate `INFO` log volume.
- User-facing toast messages use concise English UI wording consistent with the rest of the Torg Codex reader interface (feature `006-codex-web-ui`).
- Architectural decision documentation (`ADR-023`) is drafted as `Proposed` during setup and gated on explicit maintainer acceptance prior to merge rather than blocking initial implementation tasks.
