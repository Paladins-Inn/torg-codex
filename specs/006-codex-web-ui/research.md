# Phase 0 Research: Torg Codex Web User Interface

**Feature**: `006-codex-web-ui` | **Date**: 2026-11-15 | **Spec**: [spec.md](./spec.md)

All technical unknowns, framework integration patterns, architectural boundary rules, and observability details were investigated against the existing 4-module reactor (`Spring Boot 4.1.1`, `Java 25`, `JTE 3.2.3`) and accepted ADRs (`ADR-005`, `ADR-010`, `ADR-016`, `ADR-017`, `ADR-019`, `ADR-020`, `ADR-021`, `ADR-022`). Zero unresolved `NEEDS CLARIFICATION` items remain.

## D1 — Packaging & Delivery of Bootstrap 5, Bootstrap Icons, and htmx (`ADR-020`, `ADR-021`)

- **Decision**: Package frontend dependencies as self-hosted Maven WebJars in `torg-codex/pom.xml` resolved via Spring Boot 4's managed `org.webjars:webjars-locator-lite` (`1.1.4`):
  - `org.webjars:webjars-locator-lite` (version managed by `spring-boot-dependencies:4.1.1`)
  - `org.webjars.npm:bootstrap:5.3.8`
  - `org.webjars.npm:bootstrap-icons:1.13.1`
  - `org.webjars.npm:htmx.org:2.0.8`
  Templates reference version-agnostic `/webjars/...` paths (`/webjars/bootstrap/dist/css/bootstrap.min.css`, `/webjars/bootstrap/dist/js/bootstrap.bundle.min.js`, `/webjars/bootstrap-icons/font/bootstrap-icons.min.css`, `/webjars/htmx.org/dist/htmx.min.js`) alongside local theme stylesheets under `/themes/codex/codex.css` and `/themes/admin/admin.css`.
- **Rationale**:
  1. Eliminates third-party CDN requests on page load (note: legacy `login.jte` loaded Pico CSS from `cdn.jsdelivr.net`), avoiding visitor IP leakage to external CDNs in alignment with `docs/modules/arc42/pages/08_concepts/data-protection.adoc` and offline/Testcontainers test execution.
  2. Requires zero Node.js/npm/Vite build plugins in Maven (`./mvnw clean verify` works hermetically).
  3. `webjars-locator-lite` is Spring Boot 4's recommended, fast, GraalVM-native-compatible replacement for the reflection-heavy `webjars-locator-core`.
- **Alternatives considered**:
  - *External CDN links (`jsdelivr` / `unpkg`)*: Rejected — leaks user IP/browser metadata to third parties (GDPR concern) and fails in air-gapped environments.
  - *Checking minified CSS/JS/woff2 files into `src/main/resources/static/vendor/`*: Rejected — bloats git diffs and misses Dependabot/Maven dependency scanning.
  - *Separate `torg-codex-ui` npm/Vite Maven module*: Rejected — unnecessary build complexity since `ADR-020` and `ADR-021` purposefully select build-free CSS/hypermedia libraries.

## D2 — JTE Template Precompilation, Development Mode, and Safe HTML Rendering (`ADR-010`, `Principle VI`)

- **Decision**:
  1. Configure `gg.jte.usePrecompiledTemplates: true` (and remove `gg.jte.development-mode: true` from production `application.yaml`, moving `development-mode: true` / `usePrecompiledTemplates: false` to an optional local `dev` profile) so packaged Spring Boot JARs serve the classes generated by `jte-maven-plugin:3.2.3` without requiring `src/main/jte` on disk.
  2. Keep `<contentType>Html</contentType>` in `jte-maven-plugin` so JTE auto-escapes all `${...}` expressions (names, slugs, query parameters, attributes, error banners) at compile time.
  3. Confine `$unsafe{...}` output strictly to a single reusable fragment (`codex/fragments/richText.jte`) that accepts a typed `SanitizedHtml` wrapper produced exclusively from `Censor.apply(...)`.
- **Rationale**: Prevents packaged-JAR startup failures in Docker/CI while making accidental unescaped rendering of untrusted user strings structurally impossible (`Principle VI`).
- **Alternatives considered**:
  - *Keep `gg.jte.development-mode: true` in default `application.yaml`*: Rejected — `jte-spring-boot-starter-4` throws a runtime configuration/directory error when running from a packaged JAR without `src/main/jte`.
  - *Scatter `$unsafe{string}` across templates*: Rejected — error-prone and harder to audit for XSS safety.

## D3 — Common Core Entry Concept Across All 17 Catalog Areas While Preserving `EntityType` & ArchUnit `A3`

- **Decision**:
  1. Keep `de.paladinsinn.torg.codex.domain.markup.EntityType` (14 values) unchanged so `CatalogDrmArchitectureTest.a3_everyCatalogAreaRecordIsProductBound` and `EntityReferenceProcessor` remain 100% intact.
  2. Introduce `CatalogArea` (17-value enum in `torg-codex-domain`) representing all 14 product-bound areas plus `PUBLICATION`, `ARTICLE`, and `TAG`, carrying canonical UI path segment (`slug`), optional path aliases (`/groups` canonical matching `EntityType.GROUP`, `/perk-groups` alias), display titles, navigation section, icon identifier, and `Optional<EntityType> productBoundType()`.
  3. Introduce `CatalogEntry` in `torg-codex-domain.model` as the common super-interface of `ProductBoundEntry` (covering all 14 DRM-bound records) and directly implemented by `Article`, `Publication`, and `Tag`. Every entry exposes `id()`, `slug()`, `name()`, `catalogArea()`, `clearance()`, `cosmSlugs()`, and `groupings()`.
  4. Introduce framework-free `CatalogCategoryDescriptor<E extends CatalogEntry>` metadata descriptors (one per `CatalogArea`, registered in a domain `CatalogCategoryRegistry`) declaring dynamic summary table columns, active filter facets, sort extractors, and ordered detail sections (stat blocks, key-value attributes, embedded reference lists, raw prose fields to pass through `Censor`, and publication codex IDs).
- **Rationale**: Fulfills `FR-016` ("all entries adhere to a common core concept; fully generic views across all 17 catalog areas") with **one** generic reader controller, **one** generic table template, **one** generic detail template, and **one** generic teaser template—without breaking `EntityType` or weakening `CatalogDrmArchitectureTest` `A3`.
- **Alternatives considered**:
  - *Add `ARTICLE`, `PUBLICATION`, `TAG` to `EntityType`*: Rejected — violates `CatalogDrmArchitectureTest.a3_everyCatalogAreaRecordIsProductBound`, which requires every `EntityType` to implement `ProductBoundEntry`.
  - *17 separate UI controllers and 17 separate table/detail JTE templates*: Rejected — directly contradicts `FR-016` and multiplies maintenance and test surface 17×.

## D4 — Canonical Human-Readable Slugs + UUID Resolution Without Schema Migrations (`FR-005`, `FR-008`, `Principle IV`)

- **Decision**:
  1. Derive canonical slugs deterministically in `torg-codex-domain` via `CatalogSlugs`:
     - `Cosm`: returns persisted `cosm.slug()` (`"aysle"`, `"core-earth"`, etc.).
     - `Publication`: returns persisted `publication.codexId()` (`"core-rulebook"`, `"sourcebook-aysle"`, etc.).
     - Remaining 15 areas: NFKD Unicode normalization → strip combining marks → lowercase ASCII → replace non-alphanumeric runs with `-` → trim leading/trailing `-` (e.g., `"Ace Pilot"` → `"ace-pilot"`, `"Lobizón"` → `"lobizon"`, `"Changelog"` → `"changelog"`).
     - Collision safety: within a category, if two entries share the exact normalized base slug, disambiguate deterministically by appending `-<first-8-hex-of-uuid>` sorted by UUID while also keeping exact UUID lookup working.
  2. Extend `RestrictedCatalogQuery<T>` and `CatalogQuery<T>` with `findByIdentifier(String slugOrId)` (parsing as `UUID` first when matching UUID syntax, otherwise matching canonical slug against the area's entries while applying identical `CatalogAccessPolicy` DRM and observer rules!).
- **Rationale**:
  1. Makes both legacy `https://torg-codex.com` URLs (`/perks/ace-pilot`, `/articles/changelog`) and `EntityReferenceProcessor` links (`<perk:ace-pilot>` → `/perks/ace-pilot`, `<group:prowess>` → `/groups/prowess`) work out of the box alongside `/perks/<uuid>`.
  2. Requires **zero Liquibase schema changes** on the 15 UUID-only tables (catalog size per area is at most ~1,100 rows, well within fast in-memory/cached slug matching), avoiding a 3-release expand/migrate/contract cycle (`Principle IV`).
- **Alternatives considered**:
  - *Add nullable `slug` columns across 15 database tables via Liquibase*: Rejected — unnecessary schema churn across 15 tables when slugs are deterministically derived from `name` and dataset cardinality per area is ≤ 1,100 rows.
  - *UUID-only URLs*: Rejected by user clarification (`FR-005`, `FR-008`).

## D5 — Generic 17-Area Browse Service Respecting ArchUnit `A1`, `A2`, and `A6`

- **Decision**:
  - Keep all 14 `RestrictedCatalogQuery<T>` beans (`RestrictedCatalogQueryService<T>`) and the 3 concrete `CatalogQuery<Article>`, `CatalogQuery<Publication>`, `CatalogQuery<Tag>` beans (`CatalogQueryService<T>`) in `CatalogQueryConfiguration` exactly as guarded by `CatalogDrmArchitectureTest` `A6`.
  - Introduce a framework-free driving port `CatalogBrowseQuery` (`CatalogBrowseService` in `torg-codex-application`) backed by a map of 17 typed `CatalogAreaAccessor<E>` delegates wired in `CatalogQueryConfiguration`:
    - The 14 product-bound delegates wrap `RestrictedCatalogQuery<P>` (generic `<P extends ProductBoundEntry>` helper — valid under `A2`).
    - The 3 public reference delegates wrap explicit `CatalogQuery<Article>`, `CatalogQuery<Publication>`, and `CatalogQuery<Tag>` parameters (concrete type arguments — valid under `A2`, which forbids raw or type-variable `CatalogQuery<T>`).
  - Introduce `CodexOverviewQuery` (`CodexOverviewService` in `torg-codex-application`) consuming `CatalogBrowseQuery` and `CallerProductsPort` to assemble landing-page category counts and owned/missing publication summaries without any web controller touching `ProductOwnershipResolver` or `GrantedAuthority`.
- **Rationale**: Gives the UI a single generic driving port across all 17 areas while 100% of product-bound reads still pass through `RestrictedCatalogQueryService` and every existing ArchUnit test (`A1`–`A6`, `CensoringSingleMechanismArchitectureTest`) passes without weakening a single guard.
- **Alternatives considered**:
  - *Inject raw `Map<CatalogArea, CatalogQuery<?>>`*: Rejected — violates `CatalogDrmArchitectureTest` `A2` and blurs the restricted vs. public port boundary.
  - *Filter in web controllers*: Rejected — places domain filtering and grouping-metric observation in the web adapter instead of `torg-codex-application`.

## D6 — htmx Full-Page vs. Fragment Rendering & Browser Cache Safety (`ADR-021`)

- **Decision**:
  1. `GET /<category>` inspects the `HX-Request` request header (ignoring boosted full-page nav when `HX-Target` targets `#catalog-results`):
     - Standard browser request (or `HX-Request` absent): renders `codex/pages/category.jte` inside `codex/layout/page.jte` (complete HTML document).
     - Partial filter/search/sort request (`HX-Request: true` with `HX-Target: catalog-results`): renders only `codex/fragments/categoryResults.jte` (result count badge, active filter chips, `<table>` headers with updated sort links, and `<tbody>` rows) and sets `HX-Push-Url` (or relies on client `hx-push-url="true"`).
  2. Every endpoint that varies its HTML response by `HX-Request` MUST include response header `Vary: HX-Request` so browsers and proxies never serve a cached partial `<table>` fragment on full-page Back/Forward/Refresh navigation.
  3. Search inputs use `hx-trigger="input changed delay:200ms, search"` and checkboxes/selects use `hx-trigger="change"` submitting the enclosing `<form id="catalog-filter-form">`, preserving all active filter controls (`FR-004`).
- **Rationale**: Delivers sub-second partial table updates (`SC-004`) and clean bookmarkable URLs (`FR-005`) while eliminating the classic htmx `hx-push-url` back-button fragment-caching bug.
- **Alternatives considered**:
  - *Always return full `<html>` and use `hx-select="#catalog-results"`*: Simpler controller return path, but transfers redundant navbar/footer markup on every keystroke; dual template/fragment rendering is trivial in JTE because `category.jte` simply calls `@template.codex.fragments.categoryResults(...)`.

## D7 — Dedicated Login and Logout Pages & Fixing the `formLogin` Filter Conflict (`FR-014`, `SC-006`)

- **Decision**:
  1. Remove `.formLogin(form -> form.loginPage("/login").permitAll())` from `TorgCodexSecurityConfig`! Currently, Spring Security's default `UsernamePasswordAuthenticationFilter` intercepts `POST /login` (expecting `username`/`password`) before `LoginController.performLogin(@RequestParam("apiKey"))` can execute. Because all routes are `.permitAll()` with content-level DRM, removing `.formLogin(...)` while keeping `.exceptionHandling(...)` / explicit `CodexAuthController` endpoints (`GET /login`, `POST /login`, `GET /logout`) and Spring Security `.logout(logout -> logout.logoutUrl("/logout").logoutSuccessUrl("/login?logout"))` resolves the conflict cleanly.
  2. `GET /login` renders the reader-themed Bootstrap 5 page `codex/pages/login.jte` exclusively for **non-admin DriveThruRPG API-key authentication** (API-key password input, link/instructions to DriveThruRPG account key settings, optional `?logout` info alert, and error alert on invalid key). Role-based OIDC authentication (`ADR-007`) is reserved for a separate `/admin/**` `SecurityFilterChain` when the future Admin UI is introduced.
  3. `GET /logout` renders the dedicated reader-themed Logout page `codex/pages/logout.jte` displaying current signed-in status and a `POST /logout` confirmation button (plus a Cancel link back to `/`).
  4. Global navigation (`codex/layout/navbar.jte`) contains **zero** `<input>` credential fields (`SC-006`): it shows an unlock-status badge + `<a href="/login">` button when anonymous, or owned-book count + `<a href="/logout">` link when authenticated.
- **Rationale**: Directly fulfills user clarification `FR-014` / `SC-006` and fixes a latent bug in `TorgCodexSecurityConfig` where `POST /login` was hijacked by `UsernamePasswordAuthenticationFilter`.
- **Alternatives considered**:
  - *Custom `AbstractAuthenticationProcessingFilter` replacing `LoginController`*: Viable, but keeping thin `@Controller` endpoints (`GET /login`, `POST /login`, `GET /logout`) delegating to `AuthenticationManager` and `HttpSessionSecurityContextRepository` is simpler, testable via MockMvc, and renders validation errors directly in `codex/pages/login.jte`.

## D8 — Reader UI vs. Reserved Admin UI Separation (`FR-019`, `ADR-020`)

- **Decision**: Separate the two UI surfaces inside `torg-codex` across four explicit seams:
  1. **Java Packages**:
     - `de.paladinsinn.torg.codex.api..` — REST API (`@RestController`, `/api/**`).
     - `de.paladinsinn.torg.codex.web.codex..` — Reader Codex UI (`@Controller`, `/`, `/<category>/**`, `/login`, `/logout`).
     - `de.paladinsinn.torg.codex.web.admin..` — Reserved Admin UI package boundary (documented `package-info.java` + route reservation).
  2. **URL Namespaces**: `/admin` and `/admin/**` are explicitly reserved and excluded from `CatalogArea` slug resolution so no reader route can ever shadow `/admin/**`.
  3. **JTE Template Roots**:
     - `src/main/jte/codex/layout/page.jte` — Reader shell linking `/themes/codex/codex.css`.
     - `src/main/jte/admin/layout/page.jte` — Separate Admin shell linking `/themes/admin/admin.css` (ready for future Admin UI screens without touching `codex/`).
     - Remove obsolete root `src/main/jte/login.jte` (Pico CSS).
  4. **ArchUnit Guards**: Update `AdapterConventionArchitectureTest` so `@RestController` resides in `api.controller..` and `@Controller` resides in `web.codex..` or `web.admin..`, plus add a dedicated `WebUiSurfaceSeparationArchitectureTest` verifying `web.codex..` and `web.admin..` never depend on each other!
- **Rationale**: Satisfies `FR-019` and `ADR-020` cleanly inside the existing `torg-codex` self-contained service without creating a premature empty Maven module, while enforcing isolation via ArchUnit.
- **Alternatives considered**:
  - *Shared layout template with `if (isAdmin)` conditionals*: Rejected — couples navigation, theme stylesheets, and headers between two distinct personas and visual themes.

## D9 — Channel-Agnostic Domain Usage Metrics & Roll-Up Counters (`FR-017`, `SC-008`)

- **Decision**:
  1. Define framework-free driven port `CatalogUsageObserver` in `torg-codex-application.port.out`.
  2. Invoke `CatalogUsageObserver` inside `RestrictedCatalogQueryService`, `CatalogQueryService`, and `CatalogBrowseService` so **both** `/api/*` REST calls and Web UI views/filters record metrics identically without any channel tag:
     - `findAll()` on an area → `categoryAccessed(area)`.
     - `findByCosm(cosm)` → `categoryAccessed(area)` + `cosmAccessed(cosm)` (only if `cosm` is in the known cosm slug set).
     - `browse(area, criteria)` → `categoryAccessed(area)` (via the underlying `findAll()`/`findByCosm()`—ensuring exactly **one** category increment per browse call, never double-counted!) + `cosmAccessed(c)` for each valid active cosm filter + `groupingAccessed(dim, key)` for each valid active grouping filter (excluding free-text search `q`).
     - `findById` / `findByIdentifier`:
       - Accessible `ProductBoundEntry` → `detailAccessed(area, entry.slug(), DRM_GRANTED)` (+ `cosmAccessed(slug)` if `area == COSM`; + `groupingAccessed(dim, slug)` if `area` is `PERK_GROUP`, `SPELL_LIST`, `MIRACLE_LIST`, `POWER_LIST`).
       - Accessible public reference (`Article`, `Publication`, `Tag`) → `detailAccessed(area, entry.slug(), PUBLIC_REFERENCE)` (+ `groupingAccessed(TAG, slug)` if `area == TAG`).
       - Unowned `ProductBoundEntry` (`Teaser`) → `detailAccessed(area, CatalogSlugs.of(teaser.name()), TEASER)`.
       - Missing or `UNASSIGNED` (`Absent` / `Optional.empty()`) → `detailNotFound(area)` (records `outcome="not-found"`, `entry="_not_found_"`).
  3. Implement `CatalogUsageObservabilityAdapter` in `de.paladinsinn.torg.codex.api.observability` using `MeterRegistry` to maintain:
     - **4 granular counter meters**: `torg.codex.catalog.usage.category`, `torg.codex.catalog.usage.cosm`, `torg.codex.catalog.usage.grouping`, `torg.codex.catalog.usage.detail`.
     - **4 outcome roll-up counters**: `torg.codex.catalog.usage.outcome.drm.granted`, `torg.codex.catalog.usage.outcome.public.reference`, `torg.codex.catalog.usage.outcome.teaser`, `torg.codex.catalog.usage.outcome.not.found`.
     - **4 metric-family roll-up counters**: `torg.codex.catalog.usage.family.category`, `torg.codex.catalog.usage.family.cosm`, `torg.codex.catalog.usage.family.grouping`, `torg.codex.catalog.usage.family.detail`.
- **Rationale**: Satisfies every requirement of `FR-017` and `SC-008`, keeps `torg-codex-domain` and `torg-codex-application` 100% free of Micrometer (`ArchUnit A5`), prevents double-counting when `CatalogBrowseService` delegates to `RestrictedCatalogQuery`/`CatalogQuery`, and strictly bounds metric cardinality by validating filter values against known catalog entries and using a constant sentinel on `not-found`.
- **Alternatives considered**:
  - *Spring MVC `HandlerInterceptor` counting URL paths*: Rejected — misses programmatic/internal port calls, forces duplicate URL parsing across `/api/*` and UI routes, and cannot know whether a detail lookup resulted in `DRM_GRANTED`, `TEASER`, or `UNASSIGNED` without inspecting domain return values.

## D10 — Operational Logging Policy Alignment (`ADR-022`, `FR-018`, `SC-008`)

- **Decision**:
  1. Align `torg-codex/src/main/resources/application.yaml` with `ADR-022`: set default production package levels to `INFO` (`root: info`), removing hardcoded `de.paladinsinn: debug` and `de.paladinsinn.torg.codex: trace` from the production profile (moving verbose `debug`/`trace` levels to `application-dev.yaml` or test overrides where needed).
  2. Ensure all expected domain/user-level outcomes (`Invalid API key` on `POST /login`, `403` purchase `Teaser`, `404` `NotFound` entry/category) log at **`INFO`** (with structured ECS key-value fields like `catalogArea`, `outcome`, `reason` and **zero** credentials, API keys, or `ROLE_<codex-id>` authorities), reserving `WARN` for technical single-call/data anomalies (such as `CatalogAccessObservabilityAdapter`'s product-less entry warning or transient DriveThruRPG HTTP failures) and `ERROR` strictly for unhandled technical failures.
- **Rationale**: Enforces `ADR-022` and `SC-008` so 24/7 operational alerts on `ERROR` and business-hours triage on `WARN` are never polluted by user typos, bots, or locked sourcebook teasers.
- **Alternatives considered**:
  - *Logging failed logins or `403` teasers at `WARN`*: Explicitly prohibited by `ADR-022` and `FR-018` (*fachliche Fehler* belong at `INFO`).
