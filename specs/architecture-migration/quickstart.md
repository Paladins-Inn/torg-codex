# Quickstart: Validate the Architecture Migration

## Prerequisites

- JDK 25 and Docker available to Testcontainers.
- A PostgreSQL-compatible test environment and the public free-tier fixtures required by
  the repository (proprietary game CSVs are not required).
- Maven Wrapper executable from repository root.
- Recorded API compatibility fixtures created from the pre-migration baseline, organized
  by endpoint and role as defined in
  [`contracts/rest-compatibility.md`](contracts/rest-compatibility.md).

## Baseline capture (before an affected area changes)

1. Start the current application against a known fixture database.
2. For every endpoint in the REST compatibility contract, record an accessible result,
   not-found behavior, each supported `cosm` filter, authorization failure as applicable,
   and the defined role/censorship matrix.
3. Normalize only explicitly time-variant fields; retain status, headers, negotiated
   media type, JSON field presence, and collection/map order.
4. Snapshot schema metadata and representative records for the affected JPA entity
   family. Do not create or alter a Liquibase changeset.

## Per-task validation

From repository root:

```bash
./mvnw clean verify
```

Expected result: the full four-module reactor succeeds, including unit tests,
Testcontainers integration tests, REST characterization checks, WireMock tests where an
HTTP adapter changed, and ArchUnit boundary checks.

Then run the affected fixture replay against the started application and compare it with
the baseline contract:

- all response status codes, headers, negotiated media types, and JSON representations
  match;
- every defined role receives the same authorization and censored-field result;
- list/filter ordering and null handling match;
- records remain readable/writable with identical values; and
- schema comparison reports no change and the Liquibase changelog has no migration
  artifact change.

## Architecture-specific checks

Validate the target boundaries described in [data-model.md](data-model.md):

1. Domain compiles without Spring, JPA, Hibernate, or another reactor-module dependency.
2. Driving and driven ports contain only domain/Java types; application services have no
   Spring transaction annotation.
3. JPA entity ↔ domain and domain ↔ DTO conversions are generated by MapStruct in the
   designated adapters.
4. REST controllers invoke driving ports and contain only HTTP-to-domain/DTO adaptation.
5. Persistence, DriveThruRPG, AMQP, and Spring event publication are outbound adapters.
6. Architecture tests fail for a deliberately introduced unlisted violation and pass
   after it is removed.
7. Every temporary exception entry is specific and justified; final cleanup requires
   zero entries.

## Completion validation

Run `./mvnw clean verify` one final time after cleanup. Expected result: green reactor,
all compatibility fixtures identical to baseline, no Liquibase modification, no
unlisted architecture violation, and an empty exception list. Update the finalized
arc42 architecture documentation in the same cleanup sequence; do not implement any
migration code as part of this planning-only work.

## Deliberate-violation drill outcome (T121)

Performed on a scratch, uncommitted edit (never pushed/committed): added
`import org.springframework.stereotype.Component;` to
`torg-codex-domain/src/main/java/de/paladinsinn/torg/codex/domain/model/Cosm.java`.

**Result**: the build failed immediately at the **compilation** stage of the
`torg-codex-domain` module — `mvn -pl torg-codex -am test -Dtest=DomainPurityArchitectureTest`
reported:

```
[ERROR] COMPILATION ERROR :
[ERROR] .../torg-codex-domain/.../domain/model/Cosm.java:[5,38] package org.springframework.stereotype does not exist
```

This is because `torg-codex-domain`'s `pom.xml` declares no Spring dependency at all, so
any Spring import is caught even before `DomainPurityArchitectureTest`
(`ArchRuleDefinition.noClasses().that().resideInAnyPackage("de.paladinsinn.torg.codex.domain..")
.should().dependOnClassesThat().resideInAnyPackage("org.springframework..", ...)`) gets a
chance to run — the module-level dependency boundary is a *stronger* enforcement layer than
the ArchUnit rule alone, catching the violation at compile time rather than at test time.

The import was reverted immediately after observing the failure; `DomainPurityArchitectureTest`
and the full reactor were confirmed green again
(`mvn -pl torg-codex -am test -Dtest=DomainPurityArchitectureTest` → `Tests run: 1, Failures: 0`).

**Conclusion**: the drill confirms both enforcement layers work as intended —
(1) Maven dependency scoping prevents `torg-codex-domain` from ever compiling against
Spring/JPA/Hibernate, and (2) `DomainPurityArchitectureTest` (and its sibling
`ApplicationPurityArchitectureTest`, `TransactionBoundaryArchitectureTest`) would still catch
any equivalent violation that *did* have a legitimate compile-time path (e.g. a
transitively-available class), naming the specific rule violated in the failure report.
